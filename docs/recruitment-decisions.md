# 招募平台业务规则

## 1. 用户与登录

- 用户使用账号和密码注册、登录。
- 用户名必须唯一，注册后不能修改。
- 密码只保存 BCrypt 哈希，不保存明文。
- 登录成功后返回 Token。
- 后续接口从登录身份获取当前用户，不信任前端传入的用户 ID。
- 用户资料包括昵称、头像、院系、年级、个人简介和技能标签。
- 当前不接入学校邮箱认证。
- 一个用户可以同时参与多个招募。

## 2. 招募状态

招募状态只有：

- DRAFT：草稿，仅负责人可见
- RECRUITING：招募中，公开展示并允许申请
- TEAMED：已成队，不再接受申请
- CLOSED：已关闭，不再接受申请

允许的状态流转：

```text
DRAFT -> RECRUITING
DRAFT -> 删除
RECRUITING -> TEAMED
RECRUITING -> CLOSED
```

已成队和已关闭的招募不能重新开放。

## 3. 招募发布与编辑

- 只有负责人可以编辑自己的招募。
- 草稿可以完整编辑。
- 招募中可以修改描述、技能要求、截止时间和人数上限。
- 修改人数上限时，不能小于当前已确认成员数量。
- 已成队和已关闭的招募不能修改核心招募内容。
- 发布招募时必须填写标题、分类、招募目的和人数上限。
- 人数上限至少为 2 人。

## 4. 分类、课程、教师和技能

- 首批分类包括：课堂组队、学科竞赛、校园活动、其他。
- 分类使用数据库表保存，后续可以增加或禁用分类。
- 课程名称和教师名称首版使用文本字段，不对接学校教务系统。
- 技能使用标签表保存。
- 一条招募可以关联多个技能标签。
- 用户也可以拥有多个技能标签。
- 招募的技能标签用于搜索和筛选，不直接决定是否可以申请。

## 5. 人数与站外成员

- 负责人计入正式成员人数。
- 只有已经注册并确认加入的用户计入正式人数。
- 站外成员介绍只保存为文本，不计入人数，也不会自动加入群聊。
- 剩余名额计算方式：`人数上限 - 当前有效成员数量`。
- 多个用户可以同时提交申请，PENDING 申请不占用正式名额。
- 负责人可以从多个 PENDING 申请中选择接受或拒绝。
- 接受申请时必须重新检查剩余名额，并在事务中防止超员。
- 招募满员后不再接收新的申请；已有 PENDING 申请保留，直到负责人处理、招募成队或关闭。


## 6. 截止时间

- 截止时间可以为空。
- 截止时间到达后，不允许提交新申请。
- 已经提交的待处理申请仍然可以由负责人处理。
- 截止时间不会单独增加新的状态，前端根据截止时间显示“已截止”。
- 负责人可以在招募结束前修改截止时间。
- 已成队和已关闭的招募不能再修改截止时间。

## 7. 成队

- 负责人可以在成员未满时主动确认成队。
- 确认成队后，招募状态变为 TEAMED。
- 成队时所有待处理申请变为失效，并发送通知。
- 一条招募最多创建一个队伍群聊。
- 成队和创建群聊必须在同一个事务中完成。
- 成员可以主动退出队伍。
- 负责人不能直接退出，必须先转交负责人或关闭招募。
- 负责人可以移除其他正式成员。
- 负责人转交必须由新负责人确认后生效。
- 已关闭的招募不能重新开启。
