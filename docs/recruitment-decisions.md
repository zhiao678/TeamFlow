# 招募平台业务规则

## 1. 用户与登录

- 用户使用账号和密码注册、登录。
- 用户名必须唯一，注册后不能修改。
- 密码只保存 BCrypt 哈希，不保存明文。
- 登录成功后返回 Token。
- 后续接口从登录身份获取当前用户，不信任前端传入的用户 ID。
- 用户资料包括昵称、头像、院系、年级、个人简介和技能标签。
- 平台角色包括 USER 和 ADMIN，新用户默认为 USER。
- 账号状态包括 ACTIVE、RESTRICTED 和 DISABLED，新用户默认为 ACTIVE。
- 首版退出登录由前端删除本地 Token，后端暂不维护 Token 黑名单。
- 当前不接入学校邮箱认证。
- 一个用户可以同时参与多个招募。

## 2. 招募状态

招募状态只有：

- DRAFT：草稿，仅负责人可见
- RECRUITING：招募中，公开展示并允许申请
- TEAMED：已成队，不再接受申请
- CLOSED：已关闭，不再接受申请

允许的状态流转：

```text
DRAFT -> RECRUITING
DRAFT -> 删除
RECRUITING -> TEAMED
RECRUITING -> CLOSED
```

已成队和已关闭的招募不能重新开放。

- 草稿通过 `DELETE /api/recruitments/{id}` 删除，只有当前负责人可以操作。
- 关闭接口只接受 RECRUITING，不能把草稿关闭为 CLOSED，也不能关闭 TEAMED。
- 发布接口只接受 DRAFT，所有管理操作都从 JWT 身份验证当前负责人。
- 招募达到截止时间后仍保持 RECRUITING，展示截止状态由 deadline_at 决定。
- RECRUITING → TEAMED 的数据规则保留，确认成队、申请和成员管理接口在对应功能开发时落实。

## 3. 招募发布与编辑

- 只有负责人可以编辑自己的招募。
- 草稿可以完整编辑。
- 招募中可以修改描述、技能要求、截止时间和人数上限。
- 对应可修改字段为 description、requirements、tagIds、deadlineAt、maxMembers。
- 标题、分类、目的、课程和教师在发布后保持固定。PATCH 必须省略这些字段，提交非空值即返回状态冲突，即使与原值相同也应省略。
- 修改人数上限时，不能小于当前已确认成员数量。
- 已成队和已关闭的招募不能修改核心招募内容。
- 发布招募时必须填写标题、分类、招募目的和人数上限。
- 人数上限至少为 2 人。

## 4. 分类、课程、教师和技能

- 首批分类包括：课堂组队、学科竞赛、校园活动、其他。
- 分类使用数据库表保存，后续可以增加或禁用分类。
- 课程名称和教师名称首版使用文本字段，不对接学校教务系统。
- 技能使用标签表保存。
- 一条招募可以关联多个技能标签。
- 分类和技能查询只返回 enabled 为 1 的记录。禁用记录保留既有引用，新增或主动改选时必须选择启用记录。
- 用户也可以拥有多个技能标签。
- 招募的技能标签用于搜索和筛选，不直接决定是否可以申请。

## 5. 人数与站外成员

- 负责人计入正式成员人数。
- 只有已经注册并确认加入的用户计入正式人数。
- 站外成员介绍只保存为文本，不计入人数，也不会自动加入群聊。
- 剩余名额计算方式：`人数上限 - 当前有效成员数量`。
- 多个用户可以同时提交申请，PENDING 申请不占用正式名额。
- 负责人可以从多个 PENDING 申请中选择接受或拒绝。
- 接受申请时必须重新检查剩余名额，并在事务中防止超员。
- 招募满员后不再接收新的申请；已有 PENDING 申请保留，直到负责人处理、招募成队或关闭。


## 6. 截止时间

- 截止时间可以为空。
- 截止时间到达后，不允许提交新申请。
- 已经提交的待处理申请仍然可以由负责人处理。
- 截止时间不会单独增加新的状态，前端根据截止时间显示“已截止”。
- 负责人可以在招募结束前修改截止时间。
- 已成队和已关闭的招募不能再修改截止时间。

## 7. 成队

- 负责人可以在成员未满时主动确认成队。
- 确认成队后，招募状态变为 TEAMED。
- 成队时所有待处理申请变为失效，并发送通知。
- 一条招募最多创建一个队伍群聊。
- 成队和创建群聊必须在同一个事务中完成。
- 普通成员主动退出需要提交退出申请，由当前负责人批准。审核前保持 ACTIVE 并计入人数，批准后更新为 LEFT。
- 负责人退出需要从当前 ACTIVE 普通成员中选定继任者，由对方确认后，在同一事务中完成负责人变更与原负责人退出。
- 职责和工作内容交接先提供简短提示，双方自行沟通。
- 负责人可以移除其他正式成员。
- 负责人转交必须由新负责人确认后生效。
- 已关闭的招募不能重新开启。

## 8. 招募查询与当前开发边界

- 招募大厅采用分页查询，默认查询只返回招募中。显式查询 DRAFT 只返回当前负责人的草稿，游客或其他用户无法读取。负责人也可通过详情和“我的招募”查看自己的草稿。
- “我的招募”从 JWT 身份读取当前用户，返回本人全部状态的招募，按最新排序。
- 本阶段支持关键词、分类、课程、教师、状态、技能标签和最少剩余名额，以及 LATEST、DEADLINE、POPULAR 排序。具体参数和分页结构以 `recruitment-api-spec.md` 为准。
- DEADLINE 将有截止时间的记录按时间升序排列，未填写截止时间的记录放在最后，同值使用 ID 稳定排序。
- 空结果返回总数为 0 的正常分页，不作为业务异常。
- 收藏和通知功能已接入，重复收藏、取消未收藏及重复通知事件使用幂等处理。
- 申请、成员查询与移除、退出审核、负责人退出继任及通知已接入。聊天、屏蔽、举报按后续阶段推进。

## 9. 后续数据基础

| 对象 | 状态或关键业务约束 |
| --- | --- |
| recruitment_favorite | 用户与招募组合主键，取消收藏删除关系 |
| leader_transfer | PENDING → ACCEPTED / REJECTED / CANCELLED / EXPIRED，同招募至多一笔待确认，必须由接收人同意后生效 |
| member_exit_request | PENDING → APPROVED / REJECTED / EXPIRED，同成员同招募至多一笔待审核。批准后才减少正式成员人数 |
| conversation | DIRECT / TEAM，状态 ACTIVE / READ_ONLY。规范化用户对唯一，TEAM 的 recruitment_id 唯一 |
| conversation_member | ACTIVE / LEFT / REMOVED，用户与会话组合主键，已读位置必须属于同一会话 |
| message | VISIBLE / HIDDEN，客户端发送幂等键按会话及发送者唯一，隐藏保留原记录 |
| notification | read_at 为空表示未读，同接收者及 event_key 唯一，目标采用真实外键与互斥 CHECK |
| user_block | 有向用户对主键，禁止自我屏蔽，任一方向的屏蔽禁止两人私聊发送 |
| report | PENDING → PROCESSING → RESOLVED / DISMISSED，也允许直接从 PENDING 结案。同人同目标至多一个未结案举报 |
| report_action | 处理记录只追加，操作依据必填，与真实处理结果同事务提交 |

字段类型、空值、默认值、外键、索引和完整 ER 关系见 `recruitment-er.md`，DDL 以 `database/recruitment-init.sql` 为准。消息和举报只存最小必要证据，管理员不能凭角色直接浏览全部私信。

当前 owner_id 表示现任负责人，“我的招募”按 owner_id 查询，转交后由新负责人管理。原负责人可通过转交历史查看关联记录，独立的创建历史展示口径待小组确认。

## 10. 事务与并发约定

- 创建招募、技能关联和负责人初始成员记录必须原子提交。
- 编辑、发布、关闭、删除统一锁定招募行后重新校验负责人和状态，防止检查后被其他请求改变。
- 申请与成员功能开发时，所有名额和有效成员变更先锁同一招募行，再检查人数。数据库生成列唯一约束限制重复待处理申请与多名有效负责人。
- 接受申请、成队、成员退出、负责人转交、通知写入分别在对应业务事务中完成。成队与唯一群聊必须一次提交。
- 转交生效时先降原负责人角色，再提升接收人，同时修改 owner_id，避免触发单一有效负责人的唯一约束。
- 私聊发送和屏蔽统一按用户 ID 升序锁用户行，再锁会话，防止不存在屏蔽记录时发生检查后写入竞态。
- 同一会话发送持有会话锁至提交，已读位置只向前推进，幂等发送键与通知事件键必须在重试中复用。
- 多资源操作按用户、招募、会话及子记录的统一顺序加锁。出现死锁时有限重试并重新校验业务状态。
- 普通 CHECK 负责枚举及行内互斥规则，跨表人数、成员资格、ADMIN 权限和负责人一致性由服务端事务保证。
- 初始化 SQL 要求 MySQL 8.0.16 及以上版本，仅用于可重置开发库。正式升级先备份并单独迁移，保留已有历史。
