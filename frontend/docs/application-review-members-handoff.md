# 负责人申请审核与成员展示交接

## 分工与目标

完成“查看申请 → 接受或拒绝 → 刷新成员和名额”的流程。

本文基于当前 `main` 和本周任务整理，当前为待实施任务。
接口以[最新 API 规范](../../docs/recruitment-api-spec.md)为准，不使用模拟成功数据。

## 现有代码入口

- “我的招募”：`src/views/recruitment/MyRecruitmentsView.vue`。
- 编辑管理：`src/views/recruitment/RecruitmentEditorView.vue`。
- 查询/管理请求：`src/api/recruitment-query.ts`、`src/api/recruitment-management.ts`。
- 详情页不另建一套招募详情和公共布局。

## 需要完成

### 1. 负责人申请管理

- 在“我的招募”及合适的管理区域增加“管理申请”入口。
- 建议新建 `/my-recruitments/:id/applications`，设置 `meta.requiresAuth`，只实现公共布局的内容区。
- 展示申请列表和申请详情：昵称、自我介绍、技能说明、可投入时间、申请时间、状态、处理结果。
- 只有 `RECRUITING` 招募的 `PENDING` 申请提供接受/拒绝操作；其他状态展示结果。
- 注意：截止前提交的待处理申请，在截止后仍可审核，不因截止时间直接禁用审核。
- 拒绝可填写原因，最多 255 字符，可留空；提供确认与取消，取消不发请求。
- 防止重复提交，明确每条记录的操作中状态和失败提示。
- 接受/拒绝成功后刷新申请列表及招募详情；接受后同时刷新正式成员。
- `409` 表示名额或状态冲突：提示并重新查询实际结果，不自动反复接受，不本地增加人数。
- 若审核成功而随后刷新失败，应明确“操作成功，刷新失败”，提供刷新入口，不让用户误以为需要再次提交。

### 2. 成员与名额展示

- 提供正式成员列表组件及查询封装，由浏览负责人嵌入招募详情。
- 成员展示昵称、头像（为空时使用文字头像）、角色和加入时间。
- 成员响应的 `id` 是用户 ID，供申请区域判断当前用户是否已在队；不要当成成员关系记录 ID。
- 人数、人数上限和剩余名额从最新招募详情读取，不用列表页旧值或待处理申请数推算。
- 接受成功后刷新详情、成员和申请；页面再次进入时重新读取，避免旧缓存持续显示。
- 向浏览负责人提供明确的成员加载状态、错误和重试，以及刷新方法/事件。
- 负责人、正式成员不应出现申请入口；满员禁用申请。具体入口渲染由浏览模块处理。

## 接口

下列为完整后端路径，使用公共 Axios 时省略 `/api`。

| 接口 | 权限与用途 |
| --- | --- |
| `GET /api/recruitments/{id}/applications` | 负责人查询该招募申请，返回数组 |
| `PATCH /api/applications/{id}/accept` | 接受待处理申请，返回更新后的申请对象 |
| `PATCH /api/applications/{id}/reject` | 请求体可选 `{ reason }`，返回更新后的申请对象 |
| `GET /api/recruitments/{id}/members` | 公开招募可供游客查询，返回 ACTIVE 正式成员数组 |
| `GET /api/recruitments/{id}` | 获取最新招募状态、负责人和人数信息 |

申请对象已有字段：`id/recruitmentId/recruitmentTitle/applicantId/applicantDisplayName/`
`introduction/skillsDescription/availableTime/status/rejectionReason/createdAt/processedAt`。

成员对象为 `{ id, displayName, avatarUrl, role, joinedAt }`，角色 `LEADER/MEMBER`，
服务端已按负责人优先、其余加入时间及用户 ID 排序。保留该顺序。

## 缺失字段的临时处理

本周希望展示的申请者院系、年级、简介和个人技能，目前没有出现在 `ApplicationVO` 中，
也没有供负责人读取其他用户资料的已约定接口。

- 可以先设计独立的资料展示区域，但缺失字段隐藏，或整体提示“详细资料暂不可用”。
- 当前已返回的昵称、技能说明、自我介绍和可投入时间正常展示。
- 不将缺失字段描述为“用户未填写”，不复制当前登录用户资料充当申请者资料。
- 不自行增加后端字段，不调用 `/users/me` 获取申请者资料。
- 后端补齐后再集中扩展类型和映射，不阻塞现有审核链路。

## 与其他模块的对接

- 申请类型与接口集中在 `src/types/application.ts`、`src/api/applications.ts`；
  提前约定审核方法并协调修改，避免双方建立不同的 Application 类型。
- 本模块负责 `src/api/members.ts`、成员类型和 `src/components/recruitment/RecruitmentMembers.vue`（建议命名）。
- 浏览负责人只在详情页接入成员组件并使用其数据判断申请资格；本模块不大幅修改详情外壳。
- 约定业务成功后的刷新方法或事件，使申请状态、成员与名额一起刷新；保留失败重试。
- 管理页可接受 `applicationId` query 以便后续定位；当前通知只有申请 ID，缺少招募 ID，
  暂由公共模块跳“我的招募”，再由用户进入对应管理页，不新增未约定的解析接口。
- 接受/拒绝产生的通知由后端创建；前端只在操作完成后通知公共模块刷新未读数。
- 公共路由、导航、Axios、Token 和 401 由公共模块统一维护，不重复实现或覆盖。

## 交付验收

- 负责人能从我的招募进入申请管理，其他用户访问显示无权限，草稿不可见/招募不存在按响应处理。
- 无申请时显示空状态；请求失败有重试，不显示成“暂无申请”。
- 接受后申请变为 ACCEPTED，成员出现且名额更新；拒绝后状态及原因正确。
- 截止前提交的申请在截止后仍可审核；已成队、已关闭等不允许操作的情况正确反馈。
- 用两个并发接受请求测试最后一个名额：冲突方收到 409 后刷新真实数据，无假成功或人数超限。
- 各页面具备加载、失败、重试及无权限状态，正确处理 `400/401/403/404/409/500`。
- 运行 `npm run lint:check`、`npm run format:check`、`npm run build`，和浏览模块完成两账号全流程验收。
- 交付时列出已接入接口、资料字段预留情况、已知限制和测试结果。
